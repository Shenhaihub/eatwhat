# 2. 产品概述

## 2.1 产品名称

**EatWhat**

## 2.2 产品口号

主文案：

> 今天吃什么？

辅助文案：

> 是啊，吃什么。

## 2.3 产品背景

日常吃饭场景中，用户常常面对以下问题：

- 不知道自己想吃什么；
- 浏览大量商家后仍然无法决定；
- 不清楚附近有哪些符合当前胃口的食物；
- 有大致偏好，但缺少明确选择；
- 希望参考其他人在相同时间段吃什么；
- 希望快速获得少量、明确、可解释的选项。

传统地图和本地生活软件通常提供大量商家列表，而 EatWhat 的目标不是增加更多选择，而是减少选择数量。

## 2.4 产品定位

EatWhat 是一个饮食选择辅助工具。

它根据用户当前的：

- 胃口；
- 忌口；
- 口味；
- 预算；
- 距离；
- 用餐时间段；
- 明确或不明确的食物倾向；

为用户推荐食物类型，并进一步查询附近对应餐饮商家。

## 2.5 一句话价值

> 通过少量问题、可选 AI 分析和附近餐饮地点，帮助用户快速从“什么都可以”走向“就吃这个”。

## 2.6 产品边界

EatWhat 可以：

- 推荐食物种类；
- 根据真实 POI 查询附近商家；
- 根据用户偏好解释匹配原因；
- 展示其他用户自愿共享的匿名选择；
- 展示人工配置的品牌活动；
- 帮助用户缩小选择范围。

EatWhat 不保证：

- 某家店一定好吃；
- 某家店一定营业；
- 某家店一定参与活动；
- 推荐一定满足医疗意义上的过敏要求；
- 地图数据中的价格、评分、菜单和排队信息完全准确；
- 推荐结果替代用户自行判断。

# 3. 项目目标

## 3.1 产品目标

1. 帮助用户在较短时间内确定一个就餐方向；
2. 默认只展示最优先推荐，减少二次选择压力；
3. 用户需要时再展示另外两个备选；
4. 结合当前位置提供附近商家；
5. 让用户可参考“今天大家都在吃什么”；
6. 通过匿名共享逐步积累公共选择数据；
7. 通过满意度反馈收集改进信息。

## 3.2 工程目标

作为 GitHub 项目，需要展示：

- 响应式前端；
- React 与 TypeScript；
- FastAPI 后端；
- Supabase Auth；
- PostgreSQL；
- AI Provider；
- POI Provider；
- Mock/Live 双模式；
- API 安全；
- 限流与缓存；
- 隐私与免责声明；
- 测试；
- 云端部署；
- GitHub 工程化。

## 3.3 非目标

v1.0 暂不追求：

- 商业化；
- 大规模用户；
- 付费会员；
- 复杂社交；
- 精确营养建议；
- 医疗级忌口或过敏判断；
- 商家评价系统；
- 美团私有数据；
- 实时排队；
- 菜单和团购；
- 导航；
- APP 原生客户端；
- 复杂管理后台。

# 4. 目标用户

## 4.1 核心用户

- 不知道今天吃什么的学生；
- 不知道午餐或晚餐吃什么的上班族；
- 在陌生地点想快速找吃的用户；
- 容易产生选择困难的用户；
- 希望参考他人选择的人。

## 4.2 使用环境

- 电脑浏览器；
- 手机浏览器；
- 中国大陆网络环境；
- 午餐、晚餐、夜宵等常见场景。

## 4.3 用户痛点

```text
打开地图
→ 看到大量商家
→ 不知道选什么类别
→ 不断翻看
→ 仍然无法决定
```

EatWhat 的目标流程：

```text
回答少量问题
→ 获得一个首选食物类型
→ 查看附近五家商家
```

# 5. 用户角色

## 5.1 未登录访客

可以：

- 查看登录页；
- 查看注册页；
- 阅读项目介绍；
- 查看免责声明；

- 查看个人历史；
- 提交匿名共享；
- 使用每日三次额度。

## 5.2 已注册用户

可以：

- 登录；
- 每天使用三次 AI 智能推荐；
- 使用不消耗额度的自主选择流程；
- 点击活动横幅；
- 查看“今天大家都在吃什么”；
- 查询附近商家；
- 查看个人推荐历史；
- 删除个人历史；
- 清空个人历史；
- 自愿匿名共享；
- 提交满意度反馈。

## 5.3 公共演示账户

用途：

- 让 GitHub 访问者快速体验；
- 不要求每个人注册；
- 展示完整流程。

规则：

- 仅提供一个；
- 使用公开演示邮箱和密码；
- 每天自动恢复额度；
- 演示历史可定期清空；
- 不保存真实个人资料；
- 页面明确提示这是公共账户。

## 5.4 开发者/配置维护者

v1.0 不开发完整管理后台。

开发者通过配置文件维护：

- 活动横幅；
- 演示地点；
- Mock 商家；

- 模型与地图开关；
- 全局调用限制。

# 7. 核心使用场景

## 7.1 场景一：用户不知道吃什么

```text
登录
→ 点击开始我的推荐
→ 回答固定问题
→ 没有选择明确食物
→ AI 追加 1～2 个问题
→ 用户回答
→ AI 推荐三种食物
→ 默认展示首选
→ 用户确认
→ 获取位置
→ 展示附近五家商家
```

## 7.2 场景二：用户已经知道想吃什么

```text
登录
→ 点击开始我的推荐
→ 回答问卷
→ 在食物类型中选择麻辣烫
→ 跳过 AI
→ 获取位置
→ 展示附近麻辣烫
```

不消耗 AI 推荐次数。

## 7.3 场景三：用户点击活动

```text
首页
→ 点击“疯狂星期四”
→ 获取或复用当前位置
→ 搜索附近肯德基
→ 展示五家门店
```

不调用 AI，不消耗次数。

## 7.4 场景四：用户参考公共选择

```text
首页
→ 点击“今天大家都在吃什么”中的汉堡
→ 获取或复用位置
→ 搜索附近汉堡商家
```

不调用 AI，不消耗次数。

## 7.5 场景五：用户完成推荐后共享

```text
推荐完成
→ 询问是否匿名共享
→ 用户同意
→ 上传结构化匿名数据
→ 加入公共统计
```

## 7.6 场景六：用户反馈满意度

```text
结果页底部
→ 有帮助 / 没帮助
→ 可选填写详细建议
```

不使用强制弹窗阻断流程。

# 8. 账户系统需求

## 8.1 v1.0 实现方式

使用：

> Supabase Auth 邮箱 + 密码

账户是云端账户，不是浏览器本地账户。

## 8.2 注册页面

字段：

- 邮箱；
- 密码；
- 确认密码；
- 同意用户协议和隐私说明；
- 注册按钮；
- 已有账号，前往登录；
- 使用演示账户。

规则：

- 检查邮箱格式；
- 检查密码长度；
- 两次密码一致；
- 重复邮箱给出错误提示；
- 成功后进入登录或直接登录，具体交互在原型阶段确定。

## 8.3 登录页面

字段：

- 邮箱；
- 密码；
- 登录按钮；
- 前往注册；
- 使用演示账户；
- v1.1 忘记密码入口占位说明。

## 8.4 保持登录

用户登录成功后，前端保存 Supabase 会话。

刷新页面后：

- 会话有效：保持登录；
- 会话失效：返回登录页。

## 8.5 v1.0 暂不实现

- 强制邮箱验证；
- 忘记密码；
- 重置密码；
- 账户注销；
- 手机号登录；
- 第三方登录。

## 8.6 v1.1 必须预留

文档、数据库和路由规划中必须标注：

- `/auth/verify-email`
- `/auth/forgot-password`
- `/auth/reset-password`
- `/settings/delete-account`

业务表必须使用 Supabase `user_id` 关联，不能使用邮箱作为主键。

# 9. 每日三次免费推荐

## 9.1 基础规则

每个注册用户每天获得三次 AI 智能推荐机会。

重置时间：

> 每天北京时间 00:00。

## 9.2 扣除条件

只有以下情况扣除一次：

```text
用户没有明确选择食物
→ 完成 AI 补问
→ AI 成功返回最终三种推荐
```

成功后扣除一次。

## 9.3 不扣次数

- 查看首页；
- 点击活动横幅；
- 查看公共选择；
- 用户自主选择食物；
- 获取位置；
- 查询附近商家；
- 查看推荐历史；
- 展开另外两个 AI 推荐；
- AI 生成补充问题；
- AI 或地图调用失败；
- 用户中途退出；
- 重新查看当前推荐结果。

## 9.4 失败规则

AI 最终推荐失败：

- 不扣次数；
- 显示重试；
- 达到重试上限后使用规则推荐降级；
- 降级结果不扣 AI 次数。

## 9.5 首页展示

首页顶部显示：

```text
今日剩余：3 次
```

额度用完后：

- 活动入口仍可用；
- 公共选择入口仍可用；
- 自主选择流程仍可用；
- AI 智能推荐入口提示明日恢复。

# 11. “今天大家都在吃什么”规则

## 11.1 设计目标

该模块在项目刚上线时可能没有足够的真实用户共享数据，因此必须同时支持：

- 真实共享数据；
- 人工预置的默认热门选项；
- 真实数据与默认选项混合展示。

页面不使用“演示数据”“假设数据”等影响观感的显眼标签，但也不得把人工预置项伪装成真实用户统计。

## 11.2 数据优先级

```text
今天当前用餐时段的真实共享数据
→ 近几周同星期、同用餐时段的真实参考数据
→ 人工预置的默认热门选项补足页面
```

真实数据始终优先。

## 11.3 真实人数展示条件

同一种食物至少有三条真实匿名共享记录时，才可以显示真实人数，例如：

```text
麻辣烫  8人
```

低于三条时：

- 不显示虚构人数；
- 不单独暴露过小的真实样本；
- 可以暂不显示该真实项；
- 或由默认热门选项补足首页卡片。

## 11.4 默认热门选项规则

项目初期允许人工配置一些默认热门食物，例如：

- 麻辣烫；
- 汉堡；
- 小碗菜；
- 黄焖鸡；
- 烧烤。

默认热门选项：

- 与真实数据使用统一的卡片视觉风格；
- 不显示“演示数据”徽标；
- 不显示虚构的“多少人选择”；
- 可使用食物名称、图标和简短文案；
- 点击后正常进入附近商家搜索；
- 不调用 AI；
- 不消耗智能推荐次数。

示例：

```text
麻辣烫
今天来点热乎的？

[看看附近]
```

## 11.5 混合展示规则

当真实数据不足以填满首页时，可以混合展示：

```text
真实数据卡片（可显示真实人数）
+
默认热门卡片（不显示人数）
```

排序原则：

1. 达到人数阈值的当天真实数据；
2. 达到人数阈值的近几周同星期参考数据；
3. 默认热门选项。

不得为默认热门选项生成虚构人数，也不得让用户误以为其人数来自真实用户。

## 11.6 UI 数量限制

为了避免首页信息过多：

- 手机端最多显示 3 项；
- 电脑端最多显示 5 项；
- 优先保持卡片数量稳定；
- 不同时展示多个复杂数据来源说明；
- 如有真实人数，只在对应真实卡片中显示。

当页面完全使用默认热门选项时，可以在标题下使用自然文案：

> 没想法？先看看这些。

无需出现“演示”“假设”或“Mock”等技术性标签。

## 11.7 点击行为

点击食物类型：

```text
确认或获取位置
→ 查询该类型附近商家
→ 展示五家
```

不调用 AI，不消耗次数。

# 13. 固定问卷

## 13.1 问卷原则

- 问题数量控制；
- 主要使用选择题；
- 用户可以返回修改；
- 清楚显示进度；
- 不询问无关隐私；
- 手机端按钮足够大；
- 避免一次展示过多选项。

## 13.2 问题一：胃口

问题：

> 今天的胃口怎么样？

选项：

- 不太想吃，想吃清淡少量；
- 正常，想吃一顿普通正餐；
- 胃口很好，想吃得丰盛；
- 不确定。

## 13.3 问题二：忌口

问题：

> 今天有哪些不想吃的东西？

选项示例：

- 辣；
- 海鲜；
- 牛羊肉；
- 香菜；
- 油腻；
- 生冷；
- 甜食；
- 暂无忌口。

支持多选。

这里只考虑一般忌口，不做过敏安全保证。

## 13.4 问题三：口味

问题：

> 今天想吃什么口味？

选项：

- 酸；
- 甜；
- 辣；
- 咸香；
- 清淡；
- 大众稳妥；
- 都可以。

可单选或有限多选，原型阶段确定。

## 13.5 问题四：明确食物类型

问题：

> 下列食物类型中，有你今天想吃的吗？

候选内容根据前面回答进行规则筛选。

示例：

- 炸串；
- 麻辣烫；
- 汉堡；
- 烧烤；
- 黄焖鸡；
- 鸡公煲；
- 盖浇饭；
- 小碗菜；
- 面；
- 粉；
- 饺子；
- 火锅；
- 日料；
- 都没有。

若用户选择明确类型：

- 直接进入地点和商家查询；
- 跳过 AI；
- 不消耗次数；
- 保存为自主选择来源。

若选择“都没有”：

- 进入后续问题或 AI 补问。

## 13.6 问题五：预算

问题：

> 今天大概想花多少钱？

建议选项：

- 20 元以内；
- 20–40 元；
- 40–70 元；
- 70–120 元；
- 120 元以上；
- 不限。

由于地图 POI 不一定有可靠人均价格，预算主要用于推荐食物类型，不承诺商家实际消费。

## 13.7 问题六：距离

问题：

> 最远愿意接受多远？

选项：

- 500 米；
- 1 公里；
- 2 公里；
- 3 公里；
- 距离无所谓。

## 13.8 用餐时间段

自动带入，可修改。

# 14. AI 补充问题

## 14.1 触发条件

仅当：

- 用户未选择明确食物类型；
- 固定问题仍不足以生成稳定推荐；
- AI 服务可用；
- 用户当天仍有额度；

才调用 AI 补问。

## 14.2 数量限制

最多：

> 1–2 个问题。

不允许无限追问。

## 14.3 格式限制

每个问题：

- 3–6 个选项；
- 只允许选择题；
- 与吃什么直接相关；
- 不重复固定问题；
- 不询问敏感隐私；
- 不询问医疗信息；
- 不生成长篇开放题。

## 14.4 输出结构示例

```json
{
  "questions": [
    {
      "id": "meal_form",
      "question": "今天更想吃哪种形式？",
      "options": [
        "汤汤水水",
        "干饭正餐",
        "小吃快餐",
        "都可以"
      ]
    }
  ]
}
```

## 14.5 AI 不可用

- 使用规则补问；
- 或直接进入规则推荐；
- 不消耗额度；
- 页面标记为基础推荐模式。

# 24. 异常和降级

## 24.1 AI 失败

- 不扣次数；
- 最多重试一次；
- 使用规则推荐；

- 尝试一次修复或重试；
- 失败后规则降级。

## 24.3 定位被拒绝

提供：

- 手动搜索地点；
- 预设演示地点；
- 只展示食物类型。

## 24.4 地图服务失败

- 显示已推荐食物；
- 提供稍后重试；
- 提供演示商家；
- 不重复无限调用。

## 24.5 附近无商家

- 扩大距离；
- 选择其他推荐；
- 重新定位；
- 查看更多推荐。

## 24.6 每日额度用完

- 显示明日恢复；
- 活动和公共选择仍可用；
- 自主选择仍可用；
- 不允许继续 AI 推荐。

## 24.7 公共数据不足

- 不伪造真实人数；
- 优先使用达到阈值的近几周真实参考；
- 使用人工预置的默认热门选项补足页面；
- 默认热门选项不显示虚构人数；
- 页面无需显示“演示数据”或“假设数据”标签；
- 默认热门选项与真实卡片保持统一视觉风格。

## 24.8 网络中断

- 保留当前问卷状态；
- 提供重试；
- 不重复扣次数。

- 可删除单条；
- 可清空；
- 可选择是否共享；
- 共享数据不包含精确位置和身份。

## 30.8 响应式

- 手机可用；
- 电脑可用；
- 手机首页不过度拥挤；
- 电脑端布局合理；
- 不出现明显横向滚动和遮挡。

## 30.9 安全

- 前端无 API Key；
- `.env` 不上传；
- 后端校验 Token；
- 接口有限流；
- 日志不记录密码和精确位置；
- Live 服务可关闭；
- Mock 模式始终可用。
