## 1. 本指南验证什么、不验证什么

### 验证（硬缺口，机械性或文案性，设计者本人执行偏差影响小）

1. **纯键盘可访问性**：P0-05 验收已确认自动化环境无法可靠派发 Tab/Enter，这个"待人工验证"缺口只有真人在真实浏览器按键才能补。
2. **预算与商家价格的文案表达**：商家页是否把"预算只影响食物方向、不保证商家价格"说清楚。注意：设计者本人回答不算"用户理解证据"，这里只做**文案自检**，真正的用户理解推迟到工程后。

### 不验证（推迟到工程后）

- 首页三路分流是否被陌生人理解；
- 问卷是否过长/过短、是否真的减少犹豫；
- 推荐理由是否让用户相信结果来自自己的回答；
- 1→3→5 是否真的降低选择压力；
- 返回修改、异常恢复的真实操作体验。

这些推迟项已登记为计划与记忆中的"待补真人数据"，工程完成后用真实或 Mock 全链路复测。

## 3. 纯键盘自测清单（约 8 分钟）

从首页开始，只允许 `Tab` / `Shift+Tab` / 方向键 / `Space` / `Enter`。逐项记录"通过 / 失败 / 现象"。

| 步骤 | 操作 | 预期 |

## 4. 预算文案自查（约 2 分钟）

打开商家结果页（演示地点，任意食物）。对照商家页实际文案回答：

1. "页面是否明确写出：预算只用于选择食物方向？"
2. "页面是否明确写出：附近商家按品类/关键词和距离匹配，不按预算筛选？"
3. "页面是否明确写出：没有可靠门店价格数据，实际消费以门店菜单为准？"
4. "页面是否出现任何暗示'符合预算的商家'、'保证不超预算'、或商家价格与预算档挂钩的表述？"

判定：

- 四题中 1–3 均为"是"且第 4 题为"否" → 文案自查通过。
- 第 4 题为"是" → 记录该表述位置，必须修订文案后再通过。
- 第 1–3 题任一为"否" → 记录缺失位置，补充文案后再通过。

注意：这一步是**文案自检**，只能证明文案把边界说清楚了，不能证明陌生人理解了。真正的用户理解数据仍登记为工程后待补项。
