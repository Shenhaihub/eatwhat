# EatWhat 预算档位与商家价格契约 v1.0

> 状态：权威专项契约  
> 决策日期：2026-07-27  
> 上游：用户最新确认、PRD v1.2  
> 下游：问卷配置、食物词典、AI schema、POI 接口、前端文案和测试

---

## 1. 决策

首版单人正餐预算使用：

1. `under_20`：20 元以下；
2. `from_20_to_30`：20–30 元，包含边界；
3. `over_30`：30 元以上，辅助文案“今天想吃好一点”。

预算只用于推荐食物方向，属于软偏好。首版附近商家不承诺符合预算。

---

## 2. 为什么不能承诺商家价格

附近商家由 POI Provider 按食物关键词/类别和距离查询。当前项目没有建立稳定、完整且可核验的门店菜单价格数据源，因此无法可靠回答：

- 用户实际会点哪些菜；
- 当前菜单和门店价格；
- 堂食、外卖、套餐、优惠后的差异；
- 单人份量和加购；
- 同一食物类型在不同门店的巨大价格跨度。

如果系统仍写“该商家符合 20–30 元预算”，就会把一个食物层启发式包装成商家事实，属于无法兑现的承诺。

---

## 3. 两层契约

### 3.1 食物推荐层

预算可以：

- 排除明显不适合某预算档的食物方向；
- 对食物候选做软排序；
- 在有词典依据时解释“这类食物通常更容易找到该预算档的选择”。

预算不能：

- 覆盖忌口等硬约束；
- 由 AI 凭常识自由猜价格；
- 把宽价格跨度食物写成必然符合；
- 断言某家门店、某份菜单或最终账单价格。

建议食物词典字段：

```json
{
  "food_code": "noodles",
  "supported_budget_tiers": ["under_20", "from_20_to_30"],
  "budget_fit_source": "curated_food_taxonomy_v1",
  "budget_fit_updated_at": "2026-07-27"
}
```

这是产品内部食物分类依据，不是商家价格数据。

### 3.2 商家查询层

默认只依据：

- 规范化食物/品牌关键词；
- 距离；
- POI 分类相关性；
- Provider 明确返回的营业等事实字段。

没有可靠价格数据时：

- 不展示人均价格；
- 不按预算过滤；
- 不标记“预算匹配”；
- 不因价格缺失排除商家；
- 明确提示实际价格以门店菜单为准。

---

## 4. 未来参考价格的准入门

只有数据同时提供以下字段，才允许进入商家卡：

```text
reference_price_per_person
price_currency
price_source
price_updated_at
price_confidence/status
```

即使具备这些字段，也只能：

- 标为“平台参考人均”；
- 用于可关闭的软排序或筛选；
- 对缺失价格显示未知；
- 明确最终实付受菜品、份量和优惠影响。

不得：

- 写“保证不超预算”；
- 把缺失价格当作超预算；
- 用 AI 补全缺失价格；
- 用过期参考价覆盖门店实际菜单。

---

## 5. UI 文案

问卷：

> 这顿饭一个人大约准备花多少？  
> 20 元以下 / 20–30 元 / 30 元以上（今天想吃好一点）

辅助说明：

> 用于选择更合适的食物方向；具体门店价格会有差异。

推荐结果：

> 预算是食物方向的参考，不代表附近每家店都在该价位。

商家页：

> 附近结果按品类/关键词和距离匹配。当前没有可靠门店价格数据，实际消费请以门店菜单为准。

---

## 6. 测试要求

- 三个档位的边界值编码一致；
- AI 不能生成具体商家价格；
- 没有价格数据的 POI 响应不出现价格字段或预算标签；
- 价格缺失不影响商家正常展示；
- 只有来源、更新时间齐全时才显示参考价；
- UI 不出现“符合预算的商家”“保证不超预算”；
- 可用性测试询问用户能否准确复述：预算影响食物方向，但不保证门店价格。

---

## 7. 对旧文档的影响

05–12 号旧技术文档尚未完成 P0-07 同步。出现以下表述时，以本契约为准：

- 旧预算区间；
- 无来源的“预算适配/符合预算”；
- 将食物词典价格范围当成门店价格；
- 让 AI 推断或承诺价格；
- POI 缺少价格仍进行预算硬筛。

P0-07 必须把本契约落实到数据库、API、AI 和测试文档。
