# 2. 测试目标

## 2.1 功能正确

确保用户能够完成：

```text
注册/登录
→ 回答问卷
→ 自主选择或AI推荐
→ 选择地点
→ 查看附近商家
→ 查看历史
→ 匿名共享
→ 提交满意度
```

## 2.2 业务规则正确

重点验证：

- 每日最多三次成功 AI 推荐；
- AI 失败不扣次数；
- 自主选择不扣次数；
- 活动和公共选择不扣次数；
- 同一请求不会重复扣次；
- 真实公共数据至少三条才显示人数；
- 默认热门项不显示虚构人数；
- 用户只能访问自己的历史。

## 2.3 安全与隐私正确

确保：

- 前端没有服务端 Secret；
- Token 无效时无法访问业务接口；
- 精确经纬度不写入数据库和普通日志；
- AI 请求不包含邮箱、用户 ID 和位置；
- 共享默认关闭；
- 删除历史后个人数据被正确删除；
- 错误响应不暴露堆栈和数据库信息。

## 2.4 作品可复现

确保新的开发者或面试官能够：

- Clone；
- 安装依赖；
- 启动 Mock 模式；
- 运行测试；
- 查看演示；
- 阅读文档。

# 5. 测试数据原则

## 5.1 固定种子

测试使用固定 Seed，保证：

- 输入相同；
- Mock 结果相同；
- 截图稳定；
- CI 可复现。

## 5.2 测试用户

至少准备：

```text
user_a
user_b
demo_user
quota_exhausted_user
new_user
```

## 5.3 不使用真实敏感信息

测试邮箱使用专门测试域名或测试账号。

不使用：

- 个人常用邮箱；
- 真实住址；
- 真实密码；
- 真实用户位置；
- 生产 API Key。

## 5.4 数据清理

每个数据库集成测试：

- 独立事务回滚；
- 或独立 Schema；
- 或测试后清理。

测试之间不能互相依赖执行顺序。

# 7. 每日额度测试

这是项目最高风险测试之一。

## 7.1 基础次数

| 场景 | 预期 |
|---|---|
| 新用户 | 剩余3次 |
| 成功1次 | 剩余2次 |
| 成功3次 | 剩余0次 |
| 第4次 | 返回429 |
| 次日 | 恢复3次 |

## 7.2 不扣次数

验证以下操作：

- 获取AI补问；
- AI失败；
- AI超时；
- AI非法JSON；
- 规则降级；
- 自主选择；
- 活动搜索；
- 公共食物点击；
- POI失败；
- 查看更多推荐；
- 刷新结果页。

## 7.3 并发

同一用户同时发出4个最终推荐请求。

预期：

```text
最多3个成功预留
至少1个被额度拒绝
used_count + reserved_count 始终不超过3
```

## 7.4 幂等

同一用户、同一 `Idempotency-Key`：

- 连续提交两次；
- 同时提交两次；
- 第一次AI成功但前端未收到响应；
- 前端网络重试。

预期：

- 只调用一次或返回已有状态；
- 只扣一次；
- 只生成一个推荐会话结果。

## 7.5 预留释放

模拟：

- AI超时；
- Provider异常；
- 进程在预留后终止；
- 超过预留有效期。

预期：

- `reserved_count`被释放；
- `used_count`不增加；
- 推荐会话标记失败；
- 用户可重新使用该次数。

## 7.6 数据库约束

直接尝试写入：

```text
used_count = 4
reserved_count = -1
used_count + reserved_count > daily_limit
```

预期：数据库拒绝。

# 8. 推荐状态机测试

允许的状态变化：

```text
draft
→ follow_up_ready
→ quota_reserved
→ generating
→ succeeded
→ merchant_search
→ completed
```

失败路径：

```text
generating
→ failed
→ rule_fallback
→ merchant_search
```

测试非法变化：

- `draft → completed`；
- `failed → succeeded` 未重试；
- `completed → generating`；
- 前端直接提交 status；
- 重复 complete。

预期：

- 返回状态冲突；
- 数据库状态不被非法修改。

# 9. AI Provider测试

## 9.1 Mock模式

Mock Provider支持：

- 正常结果；
- 超时；
- 连接失败；
- 非法JSON；
- 缺少字段；
- 重复food_code；
- 不存在food_code；
- 理由过长；
- 返回具体商家；
- 与忌口冲突。

## 9.2 补问结构

验证：

- 0–2题；
- 每题3–6选项；
- ID合法；
- 选项不重复；
- 无自由文本；
- 不询问身份、位置、医疗信息；
- 不重复固定问卷。

## 9.3 最终推荐结构

验证：

- 正好3项；
- priority为1、2、3；
- food_code合法；
- 不重复；
- 理由长度合规；
- 不出现具体商家；
- 不包含“最好吃”“一定安全”等承诺。

## 9.4 一次重试

第一次返回非法结构，第二次合法。

预期：

- 最终成功；
- 只消耗一次额度；
- 日志显示一次重试。

两次都非法：

- 规则降级；
- 不扣AI次数。

## 9.5 Prompt隐私

通过Mock抓取发送内容，断言不包含：

- 邮箱；
- user_id；
- 经度和纬度；
- 地点名称；
- 具体商家；
- Access Token；
- 完整历史。

## 9.6 Live测试

Live AI测试不在每次CI运行。

触发方式：

- 手工；
- 定时；
- Staging；
- 有Secret时的受控工作流。

验证：

- 结构化输出；
- 延迟；
- Token；
- 成本；
- 降级；
- Provider关闭开关。

# 25. 缺陷等级

## P0：阻止发布

- 数据泄露；
- 越权；
- Secret泄露；
- 额度可绕过；
- 重复扣次；
- 登录完全不可用；
- 主流程无法完成；
- 精确位置被长期保存；
- AI编造商家并展示；
- 数据库Migration破坏数据。

## P1：发布前应修复

- 某个核心页面不可用；
- 定位拒绝后无替代；
- 历史删除失败；
- 公共数据虚构人数；
- AI失败无降级；
- 手机布局严重错位；
- 演示账户不可用。

## P2：可带已知问题发布

- 次要文案；
- 小范围视觉不一致；
- 非核心浏览器轻微样式；
- 动画缺失；
- 次要性能优化。

## P3：未来优化

- 视觉增强；
- 代码重构；
- 可选筛选；
- 辅助动效。
