## 3. 稳定的用户意图

以下来自长期交流，除非用户明确改变，否则应视为稳定：

- 产品要解决真实的“今天吃什么”决策困难，不只是展示餐厅列表。
- 用户希望从想法、需求、流程、架构、数据、API、实现、测试到部署都能理解，而不是只拿到代码。
- 设计和实现应对初学者可解释、可分阶段、可验证。
- 不为了“高级”采用微服务或不必要基础设施；优先模块化单体。
- 正式业务数据不能用 JSON 文件充当数据库；JSON 可用于配置、Mock 和接口交换。
- AI 不能编造真实餐厅或未经验证的活动信息。
- 第三方密钥和 AI 密钥不能进入前端或 Git 仓库。
- 定位只在用户需要附近结果时获取，拒绝定位要有替代路径。
- 冷启动页面可以有稳定的默认内容，但不能伪造人数或制造虚假的“大家都在吃”证据。
- 用户重视原型质量，特别担心纯文字/ASCII 原型无法表现真实界面和交互。
- 需要实时维护实施计划和项目记忆，避免长期对话压缩后丢失精度。

## 4. 项目历史压缩版

### H1：先理解完整开发流程

讨论从 Android、iOS、Web 三种完整开发流程开始。逐渐纠正了“直接写代码”“JSON 就是数据库”“一开始就微服务”等常见误解，并确定需要先产出 PRD、流程、架构、数据库、API、测试和计划。

### H2：选择 Web 路线

考虑用户使用 Windows、需要快速形成跨设备演示、依赖 Codex 协作，最终选择响应式 Web。当前历史技术方向是 React + TypeScript + Vite 前端，FastAPI 模块化单体后端，PostgreSQL/Supabase Auth，第三方 AI 和高德 POI 通过后端 Provider 接入。

### H3：EatWhat 想法形成

产品从“用户不知道吃什么”出发。早期设计是问卷后查询真实 POI，再让 AI 从真实 `poi_id` 中选 3 家店。其优点是结果直接，缺点是 AI 与地图事实强耦合、成本和幻觉边界更复杂。

### H4：推荐模型转向食物类型

最终冻结文档改为：规则先筛选食物候选；如果用户已选候选，则直接跳过 AI；否则 AI 从允许集合中选择 3 个食物代码；用户再选一种，之后才按位置查 5 家真实商户。这个转向降低了 AI 编造商户的风险，但也把产品核心从“选店”改为“先选吃法”。

### H5：设计文档扩展为 01–13

形成 PRD、用户流程、信息架构、ASCII 低保真、系统架构、数据库、API、AI、隐私、MVP 计划、测试、路线图和 GitHub 协作规范。文档内容丰富，但在版本和边界上仍有冲突；“设计冻结”不等于实现准备已经完全通过。

### H6：2026-07-22 首轮 Codex 审计

审计判断：核心价值和技术栈可行，但长问卷、强制登录、首版范围、匿名分享、地图坐标/成本和大陆公开部署需要先收敛。提出“2 步输入 → 1 个主答案 → 再定位”的短流程，并创建可点击概念原型、实时实施计划和本记忆文件。

### H7：2026-07-23 用户纠正过度简化

用户明确指出：只有两步问卷无法可靠判断用户想吃什么，容易退化为盲目推荐；01–13 号文档描述的总体流程更接近真实意图。由此，短流程不再作为主方案，后续应保留时间、食量、忌口、口味、预算、距离、食物候选等多维信息，把优化重点放在呈现、默认值、条件跳过、返回修改、进度反馈和推荐依据，而不是简单删问题。

### H8：2026-07-23 混合自适应流程定型

用户明确了新的权威方向：首页社区/活动中的明确食物选择可跳过推荐，直接进入附近商家；推荐流程先问 2–3 个基础预设题，再根据答案决定后续 2–3 个预设题，之后由 AI 生成 2–3 个追问并最终生成食物候选。结果初始只展示一个，点击“更多推荐”每次增加两个。主任务完成后可以自愿评价、填写短问卷或匿名分享，不得强制。未登录用户可以使用非 AI 功能，只有真正调用 AI 时必须登录。

完成 `01_EatWhat_PRD_产品需求文档_v1.2_权威需求基线.md` 和 `00_EatWhat_统一名词表与状态定义_v1.0.md`。PRD v1.1 已标记为历史版本。后续 02–13 号文档必须以 v1.2 和名词表为上游，不得继续沿用“固定七步、AI 一次生成多题、三个候选、全站强制登录、分享可回链”等旧设计。

用户将普通单人正餐预算改为 20 元以下、20–30 元、30 元以上，并指出：如果附近商家无法遵守预算，预算问题可能成为无法兑现的承诺。最终确定预算只作为食物方向软偏好；首版 POI 没有可靠价格时不显示价格、不按预算筛选、不声称商家符合预算。未来参考价必须有合法来源、更新时间和不确定状态，也只能作为参考。

## 5. 当前历史方案（尚未全部重新确认）

以下是 01–13 和交接文档中的既有设计，不代表审计后全部继续采用：

- 核心流程要求登录。
- 每日最多 3 次成功 AI 推荐，规则直接选择不消耗额度。
- 固定问卷为 7 步：时间、食量、忌口、口味、预算、距离、食物候选。
- 用户若直接选食物候选，跳过 AI；否则 AI 可追问 0–2 次并推荐 3 个食物类型。
- 页面默认展开 1 个主推荐，另外 2 个折叠。
- 用户选定食物后，通过浏览器定位、手动区域或演示位置查询 5 家附近商户。
- 包含历史、分享、反馈、活动、“大家今天吃什么”和设置。
- 后端为 FastAPI 模块化单体；AIProvider 和 POIProvider 均有 Mock/Live。
- 数据库使用 Supabase/PostgreSQL；认证使用 Supabase Auth。
- 地图 Live Provider 计划使用高德 Web Service。

其中“AI 不编造商户”和“首个候选优先展示”值得保留；2026-07-23 已确认的新范围、顺序和参数见第 7–8 节，目前没有阻止 PRD 修订的待确认产品决策。

## 6. 2026-07-22 审计建议（未自动视为用户决定）

### R1：产品承诺

建议统一为：**EatWhat 用最少的问题，先替用户定下一种愿意吃的食物，再用真实地图信息帮助就近落实。** 不承诺 AI 判断“最好吃的店”。

### R2：两步短流程探索（已被否定为主流程）

2026-07-22 曾建议用两步输入替代 7 步问卷，并制作可点击概念原型。2026-07-23 用户明确否定其作为主流程：输入信息不足，无法支持有依据的个性化推荐。

后续可以借鉴该原型的“主次动作清楚、备选折叠、定位后置”等表现方式，但不能继承其信息删减。正式问卷保留原文档的七个信息维度；用户已确认不强求七个独立页面，可以在不丢信息的前提下合并呈现。

### R3：访客与登录

建议访客可完成规则推荐和演示/一次性附近搜索；登录用于保存历史、跨设备同步和有成本的实时 AI。共享公共演示账号不应保存真实用户输入。

### R4：实现顺序

建议顺序为：

`产品/原型收敛 → 工程骨架 → 规则推荐闭环 → 位置/POI → 登录/历史/删除 → AI/配额 → 首版社区/活动 → 系统质量与部署`

### R5：AI 职责

规则仍须能独立返回非空答案。2026-07-23 用户明确选择动态 AI 追问，而不是把 AI 限定为人工题库：AI 应根据固定问卷和上一轮回答，自由生成有针对性的下一轮多选问题。这是产品使用 AI 的核心本意。

“自由生成”只表示题目内容动态，不表示接口和安全边界无限制。服务端仍须限制问题/选项结构、轮数、长度和敏感主题，校验每轮输出；AI 不能生成商户事实、索取身份或精确位置，也不能推荐允许 food_code 集合以外的项目。

### R6：社区和活动

2026-07-22 曾建议移出核心 MVP，但用户在 2026-07-23 明确要求社区和活动进入首个版本，因此该“后置到后续版本”建议已被否定。实现顺序仍安排在核心推荐和 AI 稳定之后，但它们是首版发布前必做项。

个人使用阶段没有真实群体样本时，社区模块不得伪造人数或群体排行；默认内容与真实统计必须分区。活动仍需来源、有效期、最后核验和素材权利。

### C-004 匿名表述冲突

如果 `shared_choices` 保留 `source_user_id` 或 `source_session_id`，数据仍可在内部回链，不能称“匿名”。D-006 已确认彻底断开，因此正式设计必须移除这两个回链字段；若要保留撤回能力，只能另行设计不关联账户的匿名撤回凭据。

### C-005 规则回退为空

API 文档存在规则回退返回空 `recommendations` 的示例，违反主流程可降级承诺。实现时必须保证合法输入至少返回一个规则答案。

### C-006 来源可由客户端声明

旧 API 允许客户端提交 `source_type`。实现时来源必须由服务端执行路径派生，防止配额、历史和分享语义被伪造。

### C-007 用户/会话归属

feedback 等数据若同时有 `user_id` 和 `session_id`，必须由服务端从会话与认证身份派生并验证所有权，不能信任客户端同时提交的两个 ID。

### C-008 删除权被推迟

如果公开服务收集邮箱和历史，不应把账户删除留到 v1.1。受控演示与公众服务必须有不同发布门。

### C-009 PRD 版本漂移

文件名为 v1.1，正文和引用中仍有 v1.0/冻结版混用。下一次 PRD 收敛时统一版本和变更记录。

## 10. 技术基线与约束

### 10.1 当前倾向栈

- 前端：React + TypeScript + Vite。
- 后端：FastAPI 模块化单体。
- 数据：PostgreSQL；历史方案使用 Supabase 托管。
- 认证：Supabase Auth，后端按当前推荐使用非对称签名和 JWKS 验证。
- 地图：高德 Web Service，仅由后端持有 key。
- AI：Provider 抽象，Mock/Live 可切换，严格结构化输出。
- 测试：前后端单测、API 集成、Provider 契约、少量核心 E2E，从第一条切片开始。

### 10.2 必须遵守的实现约束

- 模块化单体，不上微服务。
- 所有 secrets 使用环境变量/密钥管理，不进前端 bundle、日志或 Git。
- Mock 与 Live 使用相同归一化契约。
- `food_code`、`question_code` 等稳定代码与展示文字分离并带版本。
- 规则引擎必须确定性、可测试、永不对合法输入返回空结果。
- 外部 AI/POI 具有超时、错误、契约校验和可恢复行为。
- 精确坐标不写入普通日志、推荐历史、URL 或公共分享。
- 浏览器 WGS84 定位在调用高德前需正确转换/统一为 GCJ-02。
- 位置上下文短 TTL、不可篡改、绑定用户或访客会话。
- 数据归属由服务端认证上下文派生；防止 IDOR。
- 数据库迁移只有一个真源；不要让 Alembic 和手工 Supabase SQL 双轨漂移。
- 单实例内存缓存/限流只在明确单实例约束下可用；多实例前换共享存储。
- 客户端不能决定 `source_type`、`user_id` 或配额是否消费。
- 自适应预设问卷由后端 Questionnaire Decision Engine 决定；推荐实现为版本化问题库、条件表和确定性决策图/DAG，而不是散落的深层 if/else 或可执行任意表达式。
- `POST /api/v1/questionnaire/next` 是公开、无 AI 的规则接口；相同问卷版本与答案必须返回相同路径，修改早期答案时返回需要失效的后续答案 ID。
- 问卷 next 接口与 recommendation_session 分工：前者只计算非 AI 问卷路径，后者在登录后承载 AI 追问、最终生成、配额和历史。
- AI 每次只生成一个追问；一次推荐最多 3 次追问调用和 1 次最终生成调用，所有调用必须幂等、可超时并受单会话预算约束。
- 用户可见额度按一次完整推荐会话计算，不按每道追问重复扣减；内部另设模型调用预算和尝试频率限制，防止通过反复放弃会话消耗 API。

### 10.3 当前外部事实

- 2026-07 时，Node 24 为 LTS；Vite 8 的 Node 版本要求与 Node 24 兼容。初始化时仍应锁定实际版本和 lockfile。
- Supabase 托管区域没有中国大陆；作品演示可行，面向大陆公众需重新评估延迟、跨境和部署/合规方案。
- 高德周边搜索和坐标转换都应纳入调用设计；基础服务采用配额/超量计费，不能假定永久免费。
- 定位和 AI 生成内容在公众发布前需要专门的隐私与适用性审查。本项目文档不是法律意见。

## 11. 数据最小化底线

### 11.1 可以按业务需要保存

- 用户明确登录后的账户标识和必要 profile。
- 推荐会话的最小状态、food_code、规则/AI来源、字典/模型版本。
- 为复现当时体验所需的最小食物展示快照。
- 用户明确打开、收藏或确认的单个商户最小快照（是否实现需再确认）。
- 最小行为事件，不含精确位置和完整自由文本。

### 11.2 默认不保存

- 精确经纬度。
- 原始定位响应。
- 全部五家仅浏览过的商户地址和距离。
- API key、访问令牌、密码或 Authorization header。
- 未经必要性证明的完整问卷原文。
- AI 原始 prompt/response 中的身份或定位信息。

### 11.3 绝不进入公开分享

- 精确位置、坐标、详细地址。
- 问卷答案、食量、忌口、口味、预算、距离。
- AI 追问和回答。
- 邮箱、昵称、设备、IP、用户标识。
- 可直接回链到单个用户的会话信息。

## 12. 产品与交互记忆

- 首页最高优先级是开始决定，不是活动横幅或公共排行。
- 移动端首个 MVP 不需要“首页/推荐/活动/我的”四项底栏；“推荐”与首页 CTA 重复。
- 时间段、食量、忌口、口味、预算、距离和食物候选等信息维度当前均应保留；是否自动带入或合并页面必须在不降低推荐依据的前提下由用户确认。
- 不能为了缩短流程而把推荐退化为随机灵感；每项结果应能追溯到问卷信息、规则或受约束的 AI 判断。
- 首页存在两条主路径：已有明确 food_code 的社区/活动入口直接去附近商家；仍然犹豫的用户进入混合自适应推荐。
- 推荐问卷不是固定七页：先问 2–3 个基础预设题，再基于答案选择 2–3 个后续预设题，同时覆盖七个信息维度。
- AI 阶段发生在预设问卷之后，生成 2–3 个有针对性的追问，再生成最终候选。
- 最终候选采用渐进披露：初始一个，“更多推荐”每次增加两个。
- 未登录用户可以完成非 AI 路径；AI 边界要求登录并恢复此前进度，不能让登录导致问卷丢失。
- 食物/商家任务完成后，评价、短问卷和匿名分享必须作为可跳过支线，不得成为完成任务的必经步骤。
- AI 等待状态不展示虚假百分比或所谓“思维过程”。提交后立即防重复；较慢时显示问题骨架和真实阶段文案；超时/断网允许幂等重试或使用已有信息继续，且不丢答案。
- 主答案先显示一个；备选折叠。
- 商户若只按关键词和距离得到，应称“最近匹配”，不能称“最好”。
- 定位授权前说明目的；用户拒绝后可手动区域或演示位置。
- 没有真实统计时用“没想法？试试这些”等明确编辑/规则语义；不要放在“大家今天吃什么”名下伪装群体行为。
- 原型验证要用任务、完成时间、卡点、换选率和接受率；不能只问“好不好看”。
- 需要覆盖 320px、键盘、焦点、错误、空结果、定位拒绝、外部超时和规则回退状态。
- 预算档位为单人 `<20`、`20–30`、`>30`；只约束食物方向，不代表商家或最终账单符合。
- 没有来源可靠的商家价格数据时，商家页不显示价格、不按预算筛选、不生成“预算匹配”标签；AI 永远不能补全未知价格。
- 正式 P0 原型已采用暖色、低干扰、任务优先的视觉方向，但品牌视觉尚未冻结；后续可用性测试优先评价理解和操作，不把审美喜好当作核心成功指标。
- 当前原型的全部操作使用原生语义控件；自动化验证环境未正确派发 Tab/Enter 激活，P0-06 必须补一条真人纯键盘整链测试。
