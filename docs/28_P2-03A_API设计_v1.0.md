# EatWhat P2-03A API 设计文档 v1.0

> 版本：v1.0（2026-08-04）
> 对应实现阶段：P2-03A Questionnaire Decision Engine 与 next API
> 配套真源：
> - `backend/app/schemas/questionnaire.py`（QuestionBankV1 / QuestionnaireRecomputeResult / 草稿）
> - `backend/app/services/questionnaire_state.py`（load_question_bank + recompute_questionnaire + 草稿 round-trip）
> - P2-03A 清单项 §4 验收规则
> 设计原则：
> 1. **字段名 1:1 对应状态机返回结构**：API 层不做任何"重命名"，完全复用 QuestionnaireRecomputeResult，避免联调时出现"前端取到 key 与文档不一致"。
> 2. **所有入参 Pydantic 校验 + HTTP 错误码固定**：请求非法→422 由 FastAPI 返回、业务非法→400/404 手写抛出；响应体统一 `application/json`。
> 3. **确定性幂等**：相同请求体多次调用 → 相同响应（不记录服务端状态，不读 cookie/session）。
> 4. **严格 G-07**：请求体任何位置不得携带 `source_type`；路由层先检查、命中即 400。
> 5. **G-13 未登录可用**：接口不要求 Authorization；草稿由前端 localStorage 管理，后端不持久化。
> 6. **错误响应体统一结构**：`{ "code": <int>, "message": "<zh>", "details": <any|null> }`（即使 FastAPI 自动返回 422 也要保持同一外层）。

## 2. 接口 1：`POST /api/v1/questionnaire/next`（P2-03A 主）

### 2.1 请求体 JSON Schema（Pydantic 模型 `QuestionnaireNextRequestV1`，`extra="forbid"`）

| 字段 | 类型 | 必填 | 校验约束 | 对应状态机入参 | 说明 |
|---|---|---|---|---|---|
| `entry_intent` | `string` | ✅ | 枚举值，仅允许 `ai_recommend` / `community` / `activity` / `user_choice`（对应 ENTRY_INTENT_VALUES） | `entry_intent: str` | 入口意图；非 recommend 入口会立即返回 `next_action=redirect_no_questionnaire_required` |
| `questionnaire_version` | `string` | ✅ | 正则 `^v[0-9]+\.[0-9]+$`；当前仅接受 `"v1.0"`；不存在的版本会 404 | `load_question_bank(version)` 再 `bank.questionnaire_version` | 用于选择问题库版本；当前只有 v1.0，字段仍保留为未来多版本兜底 |
| `answers_by_question_id` | `Record<string, string[]>` | ✅ | 对象；key 正则 `^[a-z0-9_]{2,40}$`（question_id）；value 必须是**非 null**数组（允许空数组 `[]`，表示用户清空了这道题）；数组每个元素长度 1-32 字符；单选型题目传 1 个元素、多选型题目传 ≥0 个元素 | `answers_by_question_id: dict[str, list[str]]` | 已答题目汇总；前端每次提交都把**当前所有题的答案**（含空）完整带上，不能"增量只传这次改的题"——这样状态机才能从头确定性重算 |

> **请求体严格禁止携带的字段（命中即 400，对应 G-07）**：`source_type`、`recommendation_list`、`generation_mode`。理由：推荐层的这些字段都由服务端派生，绝不允许客户端直接指派。

### 2.2 成功响应 200 JSON（直接返回 `QuestionnaireRecomputeResult` 9 大字段；嵌套 QuestionBankItem 用于题面展示）

下表标注"对应状态机字段"列说明：API 响应字段与状态机字段 **1:1 完全一致，不做任何别名转换**。

| 字段 | 类型 | 必填 | 对应状态机字段 | 说明 / 清单对齐 |
|---|---|---|---|---|
| `questionnaire_version` | `string` | ✅ | `QuestionnaireRecomputeResult.questionnaire_version` | 回显版本号，供前端做缓存 key |
| `next_questions` | `QuestionBankItem[]` | ✅ | `QuestionnaireRecomputeResult.next_questions` | 清单要求字段名 **next_questions**；直接返回 1~2 道题的完整对象（含 `question_id / title_zh / question_type / options / maps_to / display_if`），前端无需再发 GET 拉题 |
| `next_question_ids` | `string[]` | ✅ | `QuestionnaireRecomputeResult.next_question_ids` | 冗余辅助：next_questions 的 question_id 列表；顺序与 next_questions 恒等；前端可用作纯 ID 比对旧草稿 |
| `invalidated_answer_ids` | `string[]` | ✅ | `QuestionnaireRecomputeResult.invalidated_answer_ids` | 清单要求字段名 **invalidated_answer_ids**（与 P2-03 / P2-03A 两处清单的用词完全一致）；返回被作废的已答 question_id 列表；前端收到后要把对应题的 UI 清空为"未作答"状态 |
| `invalidated_answer_question_ids` | `string[]` | ❌（deprecated） | `QuestionnaireRecomputeResult.invalidated_answer_question_ids` | 兼容 P2-03 旧字段名，值恒等于 `invalidated_answer_ids`；P2-03A 文档里不推荐前端使用；P2-05 大版本可以移除 |
| `is_complete` | `boolean` | ✅ | `QuestionnaireRecomputeResult.is_complete` | true=当前入口意图下"所需必填题全部答完"，允许进入推荐生成 |
| `progress` | `integer` | ✅ | `QuestionnaireRecomputeResult.progress` | 清单要求字段名 **progress**；整数 0~100；表示"当前入口必填集合的答题进度百分比" |
| `progress_pct` | `integer` | ❌（deprecated） | `QuestionnaireRecomputeResult.progress_pct` | 兼容旧字段，恒等于 `progress`；文档不推荐 |
| `covered_dimensions` | `DimensionCoverage[]` | ✅ | `QuestionnaireRecomputeResult.covered_dimensions` | 清单要求字段名 **covered_dimensions**；MAPPABLE_DIMENSION_FIELDS 六维，每项 `{field_name, covered: bool}`；前端可用于做"维度进度条"或"已收集维度标签" |
| `completion_reason` | `string enum` | ✅ | `QuestionnaireRecomputeResult.completion_reason` | `all_required_answered` / `entry_intent_no_questionnaire_required` / `not_complete`；辅助前端做埋点、日志 |
| `required_not_yet_answered_question_ids` | `string[]` | ✅ | `QuestionnaireRecomputeResult.required_not_yet_answered_question_ids` | 当前入口下"必填但还没有效答"的 question_id 列表；前端可选展示红色必答星标 |
| `next_action` | `string enum` | ✅ | `QuestionnaireRecomputeResult.next_action` | **清单明确要求的下一步动作指引字段**，三值之一：<br>① `proceed_questionnaire`：继续答题（next_questions 非空）<br>② `proceed_generate_recommendations`：问卷完整，可以调用推荐接口（AI recommend 入口 complete 时）<br>③ `redirect_no_questionnaire_required`：该入口无需问卷（community / activity / user_choice）<br>**前端只需要按这个字段做 switch，不用再写 if (is_complete) 的复杂判断** |

> 响应字段的 Pydantic 约束全部沿用状态机 schema：`progress ∈ [0, 100]`、`QuestionBankItem` 全部 `extra=forbid`、`max_length` 沿用 G-09 长度规则。

### 2.3 `QuestionBankItem` 嵌套字段明细（next_questions 数组元素结构）

| 字段 | 类型 | 说明 |
|---|---|---|
| `question_id` | `string`，正则 `^[a-z0-9_]{2,40}$` | 问题唯一 ID，跨版本稳定 |
| `title_zh` | `string`，1~64 字符 | 中文题面（G-09 软约束） |
| `question_type` | `"single_choice"` \| `"multi_choice"` | 单/多选类型 |
| `options` | `QuestionOption[]`，1~16 项 | 选项数组 |
| `maps_to` | `DimensionMapping`，字段 {field_name, is_array, value_is_enum_value} | 该题对应哪个八维字段；前端不用处理，后端用 |
| `display_if` | `DisplayCondition` \| `null` | 该题的展示条件；前端不用处理（后端已用它算 active），仅用于 debug |
| `required_for_entry_intents` | `string[]` | 哪些入口下是必填题；前端可选用来加星标 |

`QuestionOption` 结构：

| 字段 | 类型 | 说明 |
|---|---|---|
| `option_id` | `string`，正则 `^[a-z0-9_]{2,32}$` | 选项内部 ID，跨版本可能变；前端不要用它存草稿！草稿按 value 存！ |
| `label_zh` | `string`，1~32 字符 | 选项展示文案（中文） |
| `value` | `string`，1~32 字符，语义是枚举值（如 `"lunch"`、`"from_20_to_30"`） | **草稿持久化真正用这个**；value 是语义稳定的 enum.value，跨版本不变 |

`DimensionCoverage` 结构：

| 字段 | 类型 | 说明 |
|---|---|---|
| `field_name` | `string`，属于 MAPPABLE_DIMENSION_FIELDS 六维之一 | 维度名（`meal_period / appetite / avoidances / tastes / budget / explicit_food_preference`） |
| `covered` | `boolean` | 本维度是否已收集到"有效非空"答案（多选空数组不算覆盖） |

### 2.4 错误响应统一结构（所有 HTTP 非 2xx 都必须符合这个外层；对齐 `app/core/exceptions.py` 现有约定）

```jsonc
{
  "error": {
    "code": "BAD_REQUEST",     // 字符串码（BAD_REQUEST / NOT_FOUND / VALIDATION_ERROR / INTERNAL_ERROR / ...）
    "message": "<中文一句话说明>",
    "details": null | any,     // 可选；给开发者的调试信息（422 时为 field/message 数组）
    "request_id": "abc-123"    // 对齐 X-Request-ID 头，便于联调排障
  }
}
```

> **与 v1.0 草稿不同的重要纠正**：真实项目已经在 `app/core/exceptions.py` 里约定了 `{"error":{code,message,details,request_id}}` 外层，并在 `register_exception_handlers` 中注册过 AppError/422 校验/HTTPException 三个 handler。因此 **P2-03A 不需要新写全局 handler**，直接复用现有约定即可，文档里也改为同样结构，避免实现与文档偏离。

P2-03A 接口可能出现的 HTTP 状态码与触发条件（对齐真实 handler）：

| HTTP 状态码 | error.code | message（示例） | 触发场景 | 抛出方式 |
|---|---|---|---|---|
| **400 Bad Request** | `BAD_REQUEST` | `"请求体不得携带 source_type（来源必须由服务端派生）"` | 请求 JSON 顶层或任意嵌套里检测到 key `source_type`（G-07 强约束） | 路由层抛出 `AppError(code=BAD_REQUEST, status_code=400, ...)` |
| **400 Bad Request** | `BAD_REQUEST` | `"未知 entry_intent：xxxx，允许值为 ai_recommend / community / activity / user_choice"` | 状态机 recompute 抛 `ValueError unknown entry_intent` | 路由层 `except ValueError` → `AppError(code=BAD_REQUEST, status_code=400, ...)` |
| **404 Not Found** | `NOT_FOUND` | `"不存在的问卷版本：v9.9（当前仅提供 v1.0）"` | 请求的 `questionnaire_version` 合法正则但实际 JSON 文件不存在（`FileNotFoundError`） | 路由层 `except FileNotFoundError` → `AppError(code=NOT_FOUND, status_code=404, ...)` |
| **422 Unprocessable Entity** | `VALIDATION_ERROR` | `"请求参数校验失败"` | 字段缺失、正则不匹配、类型错误、`answers_by_question_id` key/value 长度超范围、`extra` 字段触发 forbid | 由 FastAPI 自动的 `RequestValidationError` → 已注册全局 handler → 外层 `{"error":{code=VALIDATION_ERROR,...}}`；details 放 field/message 数组 |
| **500 Internal Server Error** | `INTERNAL_ERROR` | `"问卷库加载失败，请联系维护者"` | 极少：问题库加载时 `_validate_bank_integrity` 抛出的 `ValueError`（例如 display_if 引用错误——部署/版本发布错误，正常 v1.0 不会触发） | 路由层 `except ValueError as e`（FileNotFound 之外的 ValueError）→ `AppError(code=INTERNAL_ERROR, status_code=500, message="问卷库加载失败", details={reason: str(e)})` |

> **对应 EXP-000590231 FastAPI 规范要点**：不擅自造新的返回外层，统一复用 `core/exceptions.py` 既有结构；API 层不做大块拼装，只做"参数接收 → 调 service → 异常转 AppError/HTTPException → return 业务响应"；错误响应由全局 handler 统一生成。

## 3. 草稿存储约定（P2-03A 本次不做后端草稿 API；前端 localStorage 即可）

当前状态机已提供纯数据的 round-trip：
- 序列化：`QuestionnaireDraftV1.model_dump_json()` → 存 localStorage key=`eatwhat.questionnaire_draft_v1`
- 反序列化：`QuestionnaireDraftV1.model_validate_json(raw)` → 取 `entry_intent / questionnaire_version / answers_by_question_id`
- 清空草稿：前端直接 `localStorage.removeItem(...)` + 再调一次 `POST /api/v1/questionnaire/next` 传空 answers 即可

理由（符合 G-13 未登录可用）：草稿是匿名数据，不涉及隐私/账号；先不进数据库降低复杂度；登录后持久化草稿的后端 API 留 P2-04 之后做，字段结构已与 QuestionnaireDraftV1 1:1 对齐，届时几乎零修改。

## 4. G-01~G-16 合规自查（P2-03A 设计层面）

| 规则 | 本次设计的合规点 |
|---|---|
| G-07 来源必须服务端派生 | 路由层先扫描请求体的 `source_type` key，命中即 400；任何成功响应都不允许直接回显客户端传的来源类字段 |
| G-08 推荐不空 | 本接口不生成推荐（留到 P2-04 的 POST recommendations）；G-08 在 recommendations 接口里再由 P2-02 rule_engine 兜底 |
